# Защита CryptoJournal

Коротко: данные каждого пользователя защищены **в самой базе**, а не только на сайте.
Даже если кто-то обойдёт интерфейс и будет слать запросы к Supabase напрямую с публичным ключом —
он увидит и изменит только своё. Ниже — что именно сделано и что владельцу нужно включить руками.

## База данных (Supabase, миграции `0001`–`0009`)

| Защита | Что даёт |
|---|---|
| **RLS на каждой таблице** (`user_id = auth.uid()`) | чужие сделки, списки, скриншоты не видны и не меняются |
| **2FA в правилах базы** (restrictive-политики `*_mfa`, функция `mfa_ok()`) | если у пользователя включена 2FA, без кода (сессия `aal2`) база не отдаёт и не меняет ни одной строки, не даёт удалить аккаунт — даже с украденным паролем |
| Гостям (`anon`) — никаких прав на таблицы | без входа данных не получить |
| Нет `TRUNCATE` / `TRIGGER` / `REFERENCES` у пользователей | `TRUNCATE` обходит RLS — убран |
| Поле тарифа (`plan`, `plan_until`) пользователь менять не может | Pro не «выдать себе» |
| Лимиты тарифа и потолки записей — в базе | Basic: 50 сделок/мес, без подключений, 2 скриншота на сделку; Pro: 1 подключение (не Polymarket); Pro Plus: 5 (миграция 0016, `CONNECTION_LIMIT_REACHED`, `SCREENSHOT_LIMIT_REACHED`); не больше 100 сетапов/тегов/эмоций, 5000 импортов, 100 000 сделок (админа — строки в `admins`, назначаемой только в SQL Editor, — лимиты не касаются) |
| Проверки данных (`check`) | тикеры, биржи, цены, длины текстов — мусор не записать |
| Служебные функции: `security definer`, `search_path = ''`, вызов только вошедшим где нужно | нельзя подменить объекты схемы, нельзя вызвать служебное снаружи |
| **Админка** (`0005`): таблица `admins` без прав на запись из браузера, функции `admin_*` проверяют `is_admin()` | выдать Pro, увидеть пользователей или сбросить лимит может только админ, назначенный владельцем в SQL Editor; при включённой 2FA — только после кода |
| **Ключи бирж** (`0006`): секрет — в Supabase Vault (зашифрован), колонка `secret_id` браузеру не видна, читает секрет только `get_connection_secret` (service_role); прямых прав на запись в `exchange_connections` нет | ключ API нельзя вытащить ни из браузера, ни запросом к базе; при отключении биржи или удалении аккаунта секрет удаляется |
| **Серверная функция `exchange-proxy`**: только вошедший, подключение читается с правами пользователя (RLS + 2FA), к Bybit — только адреса чтения и разрешённые параметры; принимаются только ключи «Только чтение» | даже утёкший ключ не даёт торговать или выводить; чужим ключом воспользоваться нельзя |
| **Синхронизация по расписанию** (`0007`): `dispatch_sync` и `sync_secret_ok` нельзя вызвать ни гостю, ни вошедшему; функция `sync-worker` отвечает только на вызов с секретом из Vault (иначе 403) и пишет сделки только владельцу подключения; тариф Pro проверяется и при рассылке, и в самой функции | запустить чужую синхронизацию или подсунуть сделки другому пользователю нельзя |
| Хранилище скриншотов: приватное, ≤ 2 МБ, только png/jpeg/webp | файлы — только в свою папку `{user}/{свою сделку}/`, не больше 20 на сделку, перезапись запрещена; ссылки на файлы временные (1 час) |

Проверка прямо на настоящей базе (ничего не сохраняет): `supabase/tests/live_check.sql` → SQL Editor → Run.

Всё это покрыто тестами: `npm run test:db` (поднимает чистый Postgres, применяет миграции и пытается «взломать» от имени другого пользователя / гостя / без кода 2FA).

## Сайт

| Защита | Где |
|---|---|
| **Content-Security-Policy**: скрипты — только наши файлы, сеть — только наш Supabase и публичный API Hyperliquid, никаких чужих скриптов и `eval` | `vite.config.ts` (`securityMeta`, в боевой сборке) |
| Запрет работы внутри чужой страницы (защита от кликджекинга) | `src/main.tsx` |
| Во фронтенде только публичный ключ Supabase; секретный ключ нигде не хранится | `src/lib/supabase.ts`, `.env.example` |
| React экранирует весь пользовательский текст; `innerHTML` / `eval` не используются | — |
| Выгрузка CSV защищена от «формул» Excel (`=`, `+`, `@`) | `src/lib/export/tradesCsv.ts` |
| Картинки пережимаются в браузере в webp — исходный файл (и его метаданные, например геолокация) не загружается | `src/features/trades/screenshot.ts` |
| Пароль: не короче 10 символов, буквы и цифры | `src/features/auth/errors.ts` |
| 2FA (приложение-аутентификатор), смена пароля, «Выйти на всех устройствах» | Настройки → Безопасность |
| Без исходников (sourcemap) в боевой сборке | `vite.config.ts` |

## Сборка и зависимости

- GitHub Actions: права минимальные (сборка — только чтение, выкладка — только Pages), токен не сохраняется в рабочей копии.
- `npm audit` в каждой сборке: известная уязвимость уровня high и выше — сборка не выкладывается.
- Dependabot раз в неделю предлагает обновления зависимостей и действий сборки (`.github/dependabot.yml`).

## Аудит сайта (ноябрь 2026)

Проверено атаками, а не только чтением кода (`e2e/attacks.spec.ts`, `e2e/framing.spec.ts`, `supabase/tests/live_check.sql`):

| Атака | Результат |
|---|---|
| Вредный код (XSS) в названиях сетапов/тегов/эмоций, заметке, паре, бирже, имени файла импорта, заголовках и ячейках CSV | показывается как текст, не выполняется — на всех страницах |
| Скрипт, вставленный на страницу (встроенный, с чужого сайта, `onerror`) | заблокирован CSP |
| Отправка украденного на чужой адрес (`fetch` на чужой сайт) | заблокирована CSP |
| Встраивание сайта в чужую страницу (в т.ч. iframe с `sandbox`) | сайт ничего не показывает |
| Секреты и исходники в выложенных файлах | нет: только публичный ключ Supabase, без sourcemap |
| Опасные конструкции в коде (`innerHTML`, `eval`, `javascript:`-ссылки, переходы по адресу из ссылки) | нет |
| Уязвимости в зависимостях (`npm audit`) | 0 |
| Чужие данные / Pro себе / TRUNCATE / файлы в чужую папку / без кода 2FA / гость — на настоящей базе | всё отклонено (15/15) |

**Оставшиеся риски — не в коде, их закрывают настройки:**

1. **Общий адрес `d9zeen.github.io`.** Все сайты GitHub Pages одного аккаунта — это один «источник» для браузера:
   если когда-нибудь выложить на этом же аккаунте другой сайт (другой репозиторий с Pages) и в нём будет уязвимость
   или чужой скрипт — он сможет прочитать вход в дневник. Решение: **свой домен** (например, `journal.мойдомен.ru`)
   или выкладка на Cloudflare Pages (`*.pages.dev`). Пока других сайтов на аккаунте нет — риска нет.
2. **Доступ к GitHub и Supabase = доступ ко всему** (кто войдёт в них — подменит сайт или базу). Закрывается 2FA на этих аккаунтах.
3. **Перебор паролей** ограничен Supabase (лимиты на вход); дополнительно — 2FA, проверка утёкших паролей и капча
   (Supabase → Authentication → Attack Protection), когда сайт станет публичным.
4. **Регистрация без подтверждения почты** (пока выключено для удобства) — можно завести аккаунт на чужой email.
   Чужие данные это не открывает; включить подтверждение вместе со своей почтой (SMTP).



Эти настройки нельзя поменять из кода — только в панелях сервисов.

1. **2FA на аккаунтах, которые управляют всем:**
   - GitHub: Settings → Password and authentication → Two-factor authentication;
   - Supabase: аватар → Account preferences → Multi-factor authentication.
   Кто получит доступ к ним — получит доступ ко всему, никакие правила базы не помогут.
2. **2FA в самом дневнике:** сайт → Настройки → Безопасность → «Включить 2FA».
3. **Пароли в Supabase:** Authentication → Sign In / Providers → Email:
   - Minimum password length: **6** (решение владельца 06.11.2026: простые пароли разрешены, сайт проверяет только длину);
   - Password requirements: **No required characters**;
   - Prevent use of leaked passwords — выключено (иначе простые пароли сервер не примет).
   Защита аккаунта при простом пароле — 2FA (Настройки → Безопасность).
4. Когда будет своя почта (SMTP) — включить **Confirm email** (подтверждение адреса при регистрации).
