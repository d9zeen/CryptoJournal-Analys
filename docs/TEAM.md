# Работа вдвоём: как не мешать друг другу

## 1. Защита основной ветки (делает владелец руками, один раз)

GitHub → Settings → Branches → Add rule → `claude/amazing-bohr-gt7ta9`:

- **Require a pull request before merging** — без PR в основную ветку не попасть.
- **Require status checks to pass** — отметить:
  - «Типы и тесты логики»
  - «Тесты базы и защиты (RLS)»
  - «Сквозные тесты в браузере»

  С красными тестами слить нельзя.
- (по желанию) **Require approvals** — PR нельзя слить, пока его не одобрит второй человек.

Первые два пункта важнее всего: тогда никто случайно не сломает сайт.

## 2. Одна задача = одна ветка = один PR

- У каждой сессии Claude своя ветка `claude/...`. В основную ветку напрямую никто не пушит.
- Перед работой обновить ветку от основной, чтобы не работать на старом коде.

## 3. Задачи делить заранее

- Одна задача — одна Issue на GitHub, с исполнителем.
- Лучше брать разные части проекта, например:
  - один — биржи и синхронизация (`lib/sync`, `features/connections`, `supabase/functions`);
  - другой — дашборд и интерфейс (`features/dashboard`, `features/analysis`, `layout`).

  Тогда конфликтов почти не будет.

## 4. Миграции базы — главная ловушка

- Если двое одновременно создадут миграцию с одним номером (например, `0015_...`), будет конфликт.
- **Номер миграции «занимают» в Issue:** пишут в Issue «беру 0015», и только потом создают файл.
- Применять миграцию к живой базе (SQL Editor) — **только после слияния PR**.

## 5. Серверные функции

`exchange-proxy` и `sync-worker` выкладывать в Supabase **только после слияния PR** в основную ветку.

## 6. Смотреть PR друг друга

Перед слиянием полезно смотреть чужие PR. С включённым «Require approvals» это обязательно.
